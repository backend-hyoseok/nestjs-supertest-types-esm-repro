# NestJS 12 ESM: generated E2E test cannot resolve `supertest/types`

Minimal reproduction for the `supertest/types` import generated by `@nestjs/schematics` in a standard NestJS 12 ESM application.

No monorepo conversion or custom TypeScript configuration is needed. The generated application, test sources, and compiler configuration are unchanged. The failing import is intentionally retained in this repository.

## Reproduce

```sh
pnpm install --frozen-lockfile
pnpm exec tsc --noEmit --incremental false -p tsconfig.json --pretty false
```

Expected: the generated application and tests type-check successfully.

Actual: TypeScript exits with code 2:

```text
test/app.e2e-spec.ts(4,21): error TS2307: Cannot find module 'supertest/types' or its corresponding type declarations.
```

Use the root `tsconfig.json`: the generated `tsconfig.build.json` excludes tests, so `pnpm run build` does not expose this error. `--incremental false` avoids writing a TypeScript build-info cache during the comparison.

## One-line fix to compare

In `test/app.e2e-spec.ts`, change only this import:

```diff
-import { App } from 'supertest/types';
+import { App } from 'supertest/types.js';
```

Rerun the same type-check command. It exits with code 0 in the verified environment below. Restore the original import to reproduce the failure again.

The generated project uses `"type": "module"` and TypeScript `module` / `moduleResolution` set to `nodenext`. In this configuration, the extensionless `supertest/types` subpath fails to resolve; the `.js` spelling resolves the corresponding type declaration. The fix being demonstrated is for the ESM template. This reproduction makes no claim that CommonJS templates need the same change.

## How this fixture was created

The installed Nest CLI 12.0.3 was invoked with the registry schematics 12.0.3 available to it:

```sh
nest new nestjs-supertest-types-esm-repro \
  --directory nestjs-supertest-types-esm-repro \
  --package-manager pnpm --skip-git --skip-install --no-observe
```

The lockfile was copied from an existing standard fixture with the same generated dependency manifest, then successfully installed using:

```sh
pnpm install --offline --frozen-lockfile --ignore-scripts
```

Offline mode was used only for local setup with an existing package cache; a fresh machine should use the normal installation command in the reproduction section. No patched schematics package or local package override is used.

The default Nest README was replaced by this document. A `.gitignore` and this verification record were added for sharing the reproduction.

## Scope

This is independent of the monorepo conversion issue that leaves tests outside a configured TypeScript project. Making those tests part of a project can expose this existing import error, but does not cause it. This standard application demonstrates the import error without changing project membership.
